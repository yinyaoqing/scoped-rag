# 混合檢索與重排：加了什麼、量到什麼、沒量到什麼

決策日期：2026-11-24。狀態：已採用，預設模式仍為純向量。

## 決策

在既有的向量檢索之外加上三件事，三者都受同一個權限謂詞約束：

1. **關鍵字檢索（BM25）**，和向量檢索一樣在單次 SQL 查詢內完成權限過濾與排序。
2. **RRF 融合**，把兩條檢索的名次合併。
3. **Cross-encoder 重排**，只處理前兩步已經放行的片段。

`retrieve(..., mode="vector" | "keyword" | "hybrid", reranker=...)`。預設仍是 `vector`，原因見「結論」。

## 關鍵字檢索的統計量也要受權限約束

BM25 需要語料統計：每個詞出現在幾個片段（document frequency）、片段平均長度。一般做法是對整個語料預先算好。在有權限的系統裡這是一條旁路：

- 一份使用者看不到的文件會改變詞的權重，進而改變他**看得到**的文件的分數。
- 同一個查詢在那份文件加入前後分數不同，使用者就能推知「有一份我看不到的文件談到這個詞」，逐詞試探還能推知內容。

這和 [filter-in-query.md](filter-in-query.md) 講的「結果數量本身就是訊息」是同一類問題，只是訊息藏在分數裡。

所以這裡的作法是：`readable` CTE 先用權限謂詞圈出提問者可讀的片段，`n`、`avgdl`、每個詞的 `df` 全部從這個 CTE 算出來，和排序在同一次查詢完成。資料庫裡只存每個片段的詞頻（`chunk_terms`），不存任何全語料統計。

`tests/test_hybrid.py::test_hidden_documents_do_not_move_visible_scores` 檢驗這一點：加入一份只有經理可讀、塞滿查詢詞的文件之後，員工的結果與分數必須逐位元相同。

**代價**：統計量無法預先計算，每次查詢都要對可讀集合聚合一次。語料小時無感；量大時需要按權限群組快取統計量，而快取的失效條件就是授權變更。這裡沒有做。

## 中文沒有斷詞器時怎麼切詞

英數字串轉小寫，複合代碼（`FIN-204`）同時保留整體與各段；中文連續字元切成重疊的二字詞（bigram）。這是沒有斷詞器時的標準基線，不是最佳解。切詞函式只有一份（`terms.py`），建索引與查詢共用。

不用 PostgreSQL 內建全文檢索的原因：預設設定不會切中文，而要能切中文的擴充套件在 SQLite 沒有對應物，會讓兩個後端的檢索 SQL 分岔。自己存詞頻表則讓 BM25 的 SQL 在兩個後端完全相同。

## 重排器只看得到已放行的片段

重排器的介面只有 `score(query, texts)`，拿不到 store。它能改變順序，不能增加任何片段。`test_reranker_only_sees_permitted_text` 用一個會記錄輸入的重排器確認禁止文件的文字從未被送進去。

## 量測

評測集在 `evals/retrieval/set.yaml`：一家虛構公司的 26 份內部文件（切成 51 個片段）與 46 個問題，四種題型——代碼與表單編號（identifier）、口語改寫（paraphrase）、與原文用詞接近（plain）、同主題有另一份給不同對象的文件（scoped）。

模型：嵌入 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`，重排 `BAAI/bge-reranker-base`，都在本機 CPU 執行。每條檢索取 10 筆、重排 10 筆。BM25 的 `k1`、`b` 與 RRF 的 `k` 用文獻預設值，沒有對這個評測集調整。

| 設定 | hit@1 | hit@3 | hit@10 | MRR | 每題耗時 |
| --- | --- | --- | --- | --- | --- |
| 向量 | 0.674 | 0.913 | 1.000 | 0.807 | 11 ms |
| 關鍵字 | 0.674 | 0.739 | 0.826 | 0.720 | 12 ms |
| 混合（RRF） | 0.739 | 0.913 | 1.000 | 0.833 | 24 ms |
| 向量 + 重排 | 0.804 | 0.978 | 1.000 | 0.888 | 329 ms |
| 混合 + 重排 | 0.826 | 0.978 | 1.000 | 0.899 | 372 ms |

各題型的 hit@1：

| 設定 | identifier（14） | paraphrase（18） | plain（8） | scoped（6） |
| --- | --- | --- | --- | --- |
| 向量 | 0.857 | 0.556 | 0.750 | 0.500 |
| 關鍵字 | 1.000 | 0.167 | 1.000 | 1.000 |
| 混合（RRF） | 0.857 | 0.444 | 1.000 | 1.000 |
| 向量 + 重排 | 0.929 | 0.556 | 1.000 | 1.000 |
| 混合 + 重排 | 0.929 | 0.611 | 1.000 | 1.000 |

五種設定在 46 題上都沒有回傳任何提問者無權讀取的片段。這項檢查用評測集自己的授權規則在 Python 裡算，不經過 SQL 謂詞。

完整結果在 `evals/retrieval/last-run.json`，重跑：

```bash
uv sync --group dev --extra local-embed
uv run scoped-rag --embedder local eval-quality --rerank local
```

## 結論

- **重排是這裡唯一明確的改善。** 首位命中從 0.674 到 0.80 以上，相當於 46 題裡多對 6 到 7 題；前三名命中從 0.913 到 0.978。代價是每題多約 0.3 秒（CPU、10 筆）。
- **混合檢索不是全面變好。** 它把 plain 與 scoped 兩類拉到滿分，但口語改寫從 0.556 掉到 0.444：關鍵字那一條對這類問題多半是雜訊，RRF 照樣給它一半的票。
- **關鍵字單獨使用不可行。** 18 題口語改寫有 8 題在前 10 筆裡完全找不到。
- **向量在代碼類問題上沒有預期的差**（0.857）。這個嵌入模型把 `FIN-204` 切成子詞後仍保留了足夠的字面訊息，而且語料小、相近的代碼不多。語料變大後這個數字預期會下降，但這裡沒有量到。

因此預設模式維持 `vector`。在意品質而能接受延遲時用 `--mode hybrid --rerank local`。

## 這份量測的限制

- **評測集小，而且文件與問題都是本專案作者為此寫的。** 46 題裡 1 題就是 2.2 個百分點，「向量 + 重排」與「混合 + 重排」只差 1 題，不能說誰比較好。上表是同一組資料上各設定的相對比較，不是基準測試。
- **候選深度會影響結果。** 每條檢索取 40 筆時，混合檢索的 hit@1 是 0.696、MRR 是 0.796（低於純向量的 0.807），而重排後兩種第一階段的結果完全相同——因為一個提問者可讀的片段只有 20 到 40 個，重排器幾乎看到全部。深度設為 10 是為了讓第一階段有意義；兩組數字都列在這裡。
- **向量的 hit@10 是 1.000**，所以這個評測集量不到混合檢索最常被引用的好處（補回向量漏掉的片段）。要量那件事需要更大的語料。
- **PostgreSQL 的驗證只做到正確性。** 2026-11-25 以 PostgreSQL 17.12 + pgvector 0.8.7 執行：65 個測試全過、越權評測六種設定皆 `leak_rate 0.0`、品質評測五種設定的數字與 SQLite 完全相同（`evals/retrieval/last-run-postgres.json`）。語料只有 51 個片段，沒有建向量索引，所以查詢計畫、HNSW 與高選擇性過濾的互動、以及每次查詢聚合統計量的成本都沒有量到。
- 沒有做查詢改寫（HyDE、multi-query）、語意切分、可學習的融合權重。
